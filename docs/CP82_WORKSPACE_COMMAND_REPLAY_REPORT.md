# CP82 — identity-bound A2 workspace replay

**Result:** a narrow retry path now prevents a duplicate dispatch when the pinned Pydantic AI Harness resumes the same persisted tool call after a worker dies. Unknown operations remain quarantined. This is contract evidence, not live-model or general shell qualification.

## Defect and correction

CP81's synthetic restart probe sent the same task, command, and `operation_id` through two gateway processes. The gateway ignored that field, created two confirmed effects, and the workspace contained two markers. The original reproduction remains in [`cp81_workspace_replay_probe.json`](../experiment/results/cp81_workspace_replay_probe.json).

CP82 adds a small A2-only Harness wrapper. It forwards `RunContext.tool_call_id` through the upstream `Shell` capability and command-only `WorkspaceBackend`; the adapter combines that ID with the HADES task ID and a per-tool-call backend-dispatch ordinal, then hashes the result for the gateway request. This keeps multiple internal Shell/FileSystem dispatches distinct while allowing the same ordered call to replay. The model cannot choose or change the identity. No new table, scheduler, task manager, or effect ledger was added.

The gateway validates the SHA-256 identity, binds it to a canonical digest of the command in the existing `effects.request`, and serializes identity checks under the existing task row lock. An exact replay of a `CONFIRMED` request returns its saved result and original effect ID. A changed command under the same identity returns HTTP 409. A prior unresolved workspace effect is durably moved to `QUARANTINED` and blocks both same-ID and different-ID dispatch attempts. The gateway commits the effect as `DISPATCHED` before calling the runner, so a gateway crash in that window leaves a conservative unresolved record rather than authorizing another command.

## Limits and next gate

The gateway requires a stable operation identity and rejects missing identities, preventing callers from bypassing replay protection. A2 identities include the task ID, persisted tool-call ID, and deterministic backend-dispatch ordinal; same-call replay reuses that sequence. In this spike, a test-only resume coordinator cross-checks pending StepPersistence calls against authenticated task/effect summaries before each continuation: no effect means dispatch was not durably reserved, matching confirmed effects permit replay of the original call, and any uncertain task effect blocks continuation. It also blocks `WAITING` tasks, which can encode an approval or owner-action pause. This coordinator is not integrated into a general HADES runtime. The behavior does not make arbitrary shell work exactly-once. A regenerated tool-call ID is distinct; an unknown workspace result has no general canonical reconciliation path and must remain quarantined.

`StepPersistence` continues to show the original run's tool effect as `started` after replay under a new Harness run ID. An exploratory same-run resume on `pydantic-ai-harness==0.56.0` / `pydantic-ai-slim==2.56.0` was rejected by the pinned upstream API: run IDs are single-shot, and it directs callers to use `conversation_id` for grouping turns. The test coordinator rechecks that journal entry against the confirmed HADES effect on every continuation; simply reusing a run ID is unsupported. A and C now derive the gateway operation ID from the original model tool-call ID; an isolated no-network contract test exercises the Pydantic AI context and lean-loop path. This does not prove their call histories survive process restart or that an orchestrator resumes the original call. Hermes's MCP proxy does not yet supply the identity, so its workspace operations fail closed. These are integration-coverage facts, not scored candidate failures. No memory, task-completion, or semantic model score changes are implied.

The tests are in the A2 CI path. CP71 remains `BLOCKED_EXTERNAL_DEPENDENCY`; ADR-010 remains **NOT READY**.
