The prototype compares every candidate with the same local endpoint per profile. These are inference configurations, not claims that one model is objectively stronger for every task.

Both weights are official Qwen GGUF publications and use the model repositories' Apache-2.0 license. The downloaded local files are ignored by Git. Before using a profile, verify its recorded SHA-256 and start the matching Compose service. Only one model server should run at once to keep CPU load and memory use comparable. Qwen3-8B and Qwen3-14B both report `n_ctx=40,960` and `n_ctx_train=40,960`; llama.cpp caps a 65,536 request at that limit. The Compose configuration now requests 40,960 to avoid that cap warning. The prepared stronger profile therefore does not satisfy Hermes's 64,000-token minimum.

The laptop's RTX 3080 Ti is healthy locally, but this Docker environment does not discover an NVIDIA CDI vendor and has no `nvidia-ctk`; candidate runs therefore use CPU inference. This is a recorded environment limitation, not a conclusion about candidate performance on a GPU.

Read-only recheck on 2026-10-12 reports the laptop RTX 3080 Ti Laptop GPU on driver 615.71.09, at 0% utilization and 114 MiB used. The local candidate API successfully queried the active CPU `llama.cpp` endpoint at `/v1/models`: it returned Qwen3-8B Q4_K_M with `n_ctx=40,960` and `n_ctx_train=40,960`. No generation was started for this discovery check.

## Discovered homelab GPU profile

Read-only discovery on 2026-10-11 found a reachable Ollama-compatible endpoint with Qwen3.6 35B Q4_K_M available. Its loaded-model record reported an effective `context_length=65,536`, which meets Hermes Agent's verified 64,000-token floor. The `/api/ps` value is the observed serving context; the model's training-context limit was not established from this endpoint, so it is not claimed here. Other Qwen3 8B/14B entries on that endpoint report 40,960 in the model catalog.

The endpoint's four Quadro P4000 devices reported a healthy NVIDIA 580.178.04 driver through `nvidia-smi`. During a bounded generation, 250 ms samples showed GPU utilization rise from idle to peaks of 24%, 19%, 24%, and 40% across the four devices; the Ollama `llama-server` process held roughly 5.8–7.7 GiB on each. Four short native Ollama completions generated 24–95 tokens at 27.65–37.60 tokens/s (median 32.86). These are operational probes, not a benchmark or candidate comparison; prompt lengths and completion lengths were deliberately small. A final read-only check found the service active with the model still loaded, nonzero utilization, and one active client connection of unknown ownership. No further inference requests were sent. The measurements cannot establish that the endpoint is otherwise idle or attribute later load solely to these probes. No service restart, configuration change, model download, or driver change was made.

Two other homelab Ollama/OpenAI-compatible catalogs were reachable. One listed Gemma 4 12B with catalog context metadata 262,144 but had no loaded model, so its effective serving context and GPU generation were not verified. The other listed Qwen3 8B without context metadata; its effective context was not available. The laptop has a healthy RTX 3080 Ti driver but no local Ollama listener on port 11434.

This 65,536-context profile meets Hermes's context threshold, but it is not yet usable by the comparison containers: their Compose operator network is intentionally `internal: true`, and the remote homelab endpoint is outside that network. I did not widen the network or add a proxy. Current matched family screens use the same local Qwen3-8B CPU profile for A and C; a separate targeted family 2 diagnostic used Qwen3-14B on the same CPU runtime. The four direct GPU calls were discovery probes, not matched A/B/C trials.

Remote access recheck on 2026-10-12 used `ssh -tt` with `BatchMode=yes`, `StrictHostKeyChecking=yes`, and a five-second connection bound for the three documented host aliases. All three failed before authentication; no host key was accepted and no remote inference request was sent. Therefore the prior GPU health, model/context, utilization-during-generation, and throughput observations remain the verified historical discovery, while current remote service reachability and load could not be reconfirmed. The previous active client was of unknown ownership, so no additional generation was attempted. Safe GPU reuse still requires owner-provided resolvable host identity, verified host key, and an isolated route from the candidate network.

The 2026-10-12 follow-up explicitly selected the attached homelab SSH identity with `ssh -tt` and strict host checking. One documented alias did not resolve; a second returned a DNS address but the SSH client could not resolve its hostname; the third failed strict checking because no ED25519 host key is pinned in this session. No authentication or remote command succeeded. This refines the access status but does not change the historical GPU measurements above. No remote generation was attempted because the endpoint's last known active client was of unknown ownership.

Hermes Agent enforces a 64,000-token minimum context. Its API server rejected the prepared 40,960-token Qwen3-8B profile before model/tool execution. Never override context metadata to claim 64K. The discovered profile meets the numeric floor, but a future Hermes comparison still needs a common, reachable endpoint and a measured effective context of at least 64,000 tokens.

A further read-only retry on 2026-10-12 confirmed an identity was present in the SSH agent and tried `ssh -tt` against the three documented homelab hosts with batch authentication, six-second connection bounds, and `StrictHostKeyChecking=yes`. All three were rejected by host-key verification before authentication. No key was accepted, remote driver or service command ran, and no generation request was sent. The local laptop driver remained healthy. The prior generation-time utilization, loaded-model context, and throughput values therefore remain historical verified measurements; current remote health and load are still unverified.

## Candidate request bounds and error lifecycle

The current A/C comparison adapter allows a 50-second timeout per model request, at most 16 model requests per turn, at most 18 tool calls, and at most 1,024 completion tokens per response. The final family 5 screen also tells both candidates to stop using tools after the requested change, tests, diff review, and commit are complete. The operator trial client allows 600 seconds for the full request. A failed task can still have completed workspace effects; inspect its durable trace and verified workspace snapshot before any retry. A and C's short-timeout closure path was explicitly exercised. Candidate B's Hermes-process cancellation behavior remains unverified; its adapter timeout does not prove that Hermes stops work after the API client disconnects. Do not treat that path as qualified.
