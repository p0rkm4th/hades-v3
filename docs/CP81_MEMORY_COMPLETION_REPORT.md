# CP81 — bounded memory correction completion

**Status:** trusted memory completion contract implemented; repeated A/C CPU qualification completed with mixed outcomes.
**Baseline:** CP80 `1228dae4e0f85ced036345e0fd8e12372df7562f`; matched campaign source `268e34babfc18e543dee9f93fdd5b7ba9a2243de`.
**Classification:** gateway/lifecycle integration tests plus a real CPU-model A/C experiment. No GPU or Hermes model-equivalent result is claimed.

## Failure reproduced

CP75 recorded successful scalar/list CAS mutations with one confirmed task-linked `MEMORY_MUTATION` effect and the intended canonical value, while both A and C left the task `WAITING` because the model omitted `task_checkpoint(COMPLETED)`. CP75's structured correction cases made no tool call and falsely claimed success; the task was `FAILED` and the canonical value did not change. These original outcomes remain unchanged in [the CP75 report](CP75_MEMORY_CAS_REPORT.md) and [trial records](../experiment/results/cp75_memory_cas.jsonl).

The missing-checkpoint case had enough durable evidence only for a task whose required correction had been independently fixed before the candidate turn. Completing an arbitrary task from a confirmed memory write would be unsafe: the agent might select the wrong record or value, or the request might include additional work. CP81 therefore adds an exact one-correction criterion that only the authenticated orchestrator may store when creating the task.

## Contract

The version 1 `memory_correction` completion contract identifies exactly one `memory_key`, positive `expected_revision`, and desired JSON `value`. It is immutable after task creation and supports only `memory_correct`; it cannot authorize `memory_write` or multiple corrections. The gateway finalizer independently verifies, locking the canonical row through the task-state commit:

- The effect belongs to the original task, authenticated user, and memory domain.
- There is exactly one persisted effect and it is a confirmed `MEMORY_MUTATION` for the exact resource key.
- The request is the exact keyed CAS correction with the contract's revision and value.
- The persisted result and current canonical row contain the requested value at `expected_revision + 1`.
- A nonempty final response was produced without provider failure, and no task steps remain pending.

Missing, partial, extra, mismatched, or unconfirmed effects remain incomplete. A model claim without the CAS effect stays `WAITING`. Provider failure after a confirmed mutation preserves the mutation and leaves response delivery `WAITING`. Ordinary memory writes and tasks without this trusted criterion retain their existing fail-closed completion path. The framework's orchestration decision is not accepted by itself; gateway verification remains authoritative. This contract does not solve interpretation of arbitrary natural-language corrections: its authenticated caller must bind the exact key, current revision, and intended replacement from trusted user intent before the candidate acts. CP81 uses predetermined synthetic scenarios; general caller-side intent binding remains unqualified.

## Cross-restart workspace replay finding

The A2 Shell adapter and gateway have no persisted operation-call identity. In the same disposable CP81 project, I sent the same task, command, and supplied `operation_id` before and after restarting only the candidate API and gateway. `/v1/workspace/exec` ignored the extra ID, created two distinct `CONFIRMED` effects, and the named synthetic file changed from one marker to two. The sanitized probe record is [`cp81_workspace_replay_probe.json`](../experiment/results/cp81_workspace_replay_probe.json). This proves the existing request is not idempotent across restart. No real resource was touched.

I did not add a task-plus-command-derived ID: it would conflate a legitimate repeated command with replay and still fail to bind a changed request to the original operation. A defensible correction requires a stable invocation identity persisted by the caller before dispatch, exact request-digest binding and replay handling in the existing effect ledger, and quarantine/no-redispatch for unresolved outcomes. The pinned A2 `WorkspaceBackend.run()` interface supplies only command/shell/env/timeout, but the follow-up wrapper probe below establishes a supported way to pass the Harness call identity through it. Until gateway replay and uncertain-outcome semantics are implemented and verified, uncertain shell tasks must remain under review and must not be resumed into a consequential command. No new ledger or scored candidate behavior changed.

## Reuse feasibility check

In the cached A2 runner image (`pydantic-ai-harness==0.56.0`, `pydantic-ai-slim==2.56.0`), an isolated runtime probe used the actual upstream `Shell` capability and a custom `AbstractCapability.get_wrapper_toolset()` wrapper. Its `WrapperToolset.call_tool()` received nonempty `RunContext.run_id` and `tool_call_id`, and a `ContextVar` carried both through the workspace backend's `asyncio.to_thread()` call. This establishes a supported, small adapter path for forwarding invocation identity without forking Shell. The probe used a deterministic in-memory workspace and no network or model service.

The reproducible crash probe `test_step_persistence_interrupted_shell.py` then terminated a worker after one synthetic marker dispatch. After process restart, the pinned `StepPersistence` SQLite store retained the same run/tool identity as a `started` unresolved effect. `continue_run(include_interrupted=True)` exposed the pending tool call; the default continuation selected an earlier complete checkpoint without that call. This means the caller must inspect unresolved effects before resuming, regardless of which snapshot helper it uses. The test never replayed the command. Both this test and the actual Shell identity-forwarding test ran in a read-only, network-disabled container and are now in CI.

`StepPersistence` can supply a stable identity and recovery evidence, but it does not make arbitrary shell commands idempotent or reconcile their target state. A follow-up gateway experiment should pass a task-bound identity and request digest from this wrapper into the existing effect ledger, return a saved result for an exact confirmed replay, reject changed arguments, and quarantine unknown outcomes. Keep that as a bounded A2 integration spike; no scored candidate or gateway behavior changed in CP81.

The runner is intended for the disposable `test-runner` image, which has fixture database credentials and `psycopg`; candidate containers receive neither. It emits separate tool-selection, canonical mutation, durable task, durable final-response, answer-correctness, retry, and timing evidence. The phrase/negation oracle is specific to these synthetic cases and is not a general semantic evaluator. DBOS remains a reuse candidate, not an adopted task/effect authority. CP71 remains blocked on host firewall privilege; no Hypnos generation was used. ADR-010 remains NOT READY.

## Optional A2 Shell-only uncertainty check

The pinned Pydantic AI Harness `Shell` path received one synthetic HTTP 202 `QUARANTINED` result through the real HADES workspace adapter. Under the deterministic strict peer, the Harness propagated `WorkspaceUnavailableError` and aborted: one model request, one gateway request, no retry, no final answer. An isolated `--network none`, read-only-source container check passed locally; exact-SHA CI passed at `649bfce` (run `38523264803`). The initial test at `3a9b205` failed because it assumed the exception would become a model retry prompt. Running it in the existing pinned A2 image established the actual propagation behavior, and the regression now asserts that. Preserve that negative result. This is **CONTRACT TEST** evidence of no retry within this turn; it does not complete or recover the task, prove cross-process safety, or qualify live model behavior. CP80 fixtures and shared services were not used or changed.

Source review and the synthetic restart reproduction confirm that `/v1/workspace/exec` accepts task ID and command, ignores an extra `operation_id`, and creates and dispatches a fresh effect for every request. Replaying the same command after candidate/gateway restart made a synthetic file contain two markers and created two distinct confirmed effects. This is **LIVE EXPERIMENT** evidence of duplicate dispatch on this isolated fixture, not evidence about real workspaces. Keep A2 recovery unqualified and do not resume a consequential task with an uncertain workspace command until a trusted identity/reconciliation contract prevents redispatch.
