## CP81–CP82 update — 2026-10-14

The recommendation remains **NOT READY**. CP81 adds bounded positive A/C memory-correction evidence, but outcomes are mixed: scalar CAS correction plus restart/fresh-context recall passed 3/3 per candidate; structured corrections selected no tool 0/3; list mutations were canonically correct 3/3 but final-answer accuracy was 2/3 and fresh-context recall failed 0/3. These results do not support general memory reliability. Hermes remains excluded from the 40,960-token CPU profile because it is below its documented 64,000-token minimum.

CP83 adds **CONTRACT TEST** evidence for a distinct A2 revision combining Pydantic AI Harness 0.56.0 and DBOSDurability 3.2.0: three worker-death trials after a confirmed HADES workspace effect recovered the same effect without duplicate markers. A separate timed-out command remained quarantined across restart and was not redispatched; however, the runtime failed closed with no final response, leaving the task `RUNNING`. This is a promising reuse composition for confirmed-result replay, not a live-model result, complete uncertain-effect recovery, lifecycle qualification, or demonstrated net reduction in maintenance burden. DBOS is not adopted and this evidence does not change the NOT READY decision.

CP82 adds identity-bound workspace replay evidence for A2. A worker restart after the gateway confirmed a synthetic command resumed the same persisted tool call and did not duplicate its marker. Initial CP82 CI exposed a real adapter defect: one Harness call may dispatch several backend commands, so task plus tool-call ID alone collided. A dispatch ordinal fixed the 409 responses; six repeated deterministic A2 Shell-only/Shell-plus-FileSystem profiles passed in a fresh disposable project. The first failed CI result remains recorded. Exact-SHA CI for `081305a709d088f083548598f885546dbb5fe9fc` passed in run `38581168547`.

The pinned Pydantic `StepPersistence` run IDs are single-shot. Reusing an ID is rejected; after recovery under a new run, the original tool effect remains `started` even though the HADES gateway effect is `CONFIRMED`. A test-only coordinator can reconcile that journal entry against the sole HADES effect record and rejects `WAITING` tasks, but it is not integrated into a general runtime. A/C adapter identity injection now passes an isolated contract test, but persistence and cross-restart continuation for those candidates remain unqualified. Hermes's workspace adapter still fails closed without a stable invocation identity. Unknown shell effects lack a general canonical reconciliation mechanism and remain quarantined.

CP79 demonstrates DBOS can resume a retryable workflow around the existing HADES gateway (3/3 contract trials), while CP82 demonstrates the upstream Pydantic Harness can resume one persisted Shell tool call. Neither is a live-model comparison or production durability result. The DBOS spike required separate setup, worker, and verifier programs; A2 relies on Harness `StepPersistence` plus a HADES-specific workspace identity adapter. Their code footprints are not equivalent measures, and no evidence yet shows DBOS reduces HADES-specific recovery or operating complexity. Do not adopt either as a second task/effect authority.

The smallest decision-changing evidence set is: (1) prove a coordinator can select only the original unresolved Harness call, reconcile its journal state with the gateway effect, and refuse unknown outcomes; (2) run matched held-out memory correction and fresh-context recall that includes structured/list values; (3) complete protected-action and compound-operation comparisons across eligible candidates; and (4) refresh Cinder's v2 runtime/owner evidence and obtain owner-facing usability evaluation. The GPU comparison remains externally blocked; no further Hypnos generation is authorized. These gaps keep ADR-010 NOT READY and production implementation unauthorized.
